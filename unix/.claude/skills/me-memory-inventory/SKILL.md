# Memory Inventory

## 1. スキャンする

```bash
~/.claude/skills/me-memory-inventory/scripts/scan.ts > "$(mktemp -d)/scan.json"
```

置き場ごとのメモリー・索引の不整合・切れたリンク・参照しているパスと PR、そのプロジェクトで読み込まれる CLAUDE.md 類、me- スキルを JSON で出す。ファイルは書き換えない。

- `projectPath` が null の置き場は、中身から推測し、判断がつかなければユーザーに聞く
- 編集には `path` ではなく `editablePath` を使う。home-manager 管理のファイルは Nix store への読み取り専用 symlink なので、`~/dotfiles/unix/` 側の実体を指している。null なら編集先が不明なので、提案だけにとどめる

## 2. 読んで裏を取る

メモリー本文、`instructionFiles`、`globalInstructions` をすべて読む。me- スキルは description で守備範囲をつかみ、重複を疑うときだけ本文を読む。

メモリーは書かれた時点の事実なので、PR・ブランチ・パス・コマンドが今どうなっているかを確かめてから判定する。

- PR の repo が特定できなければ「未確認」とし、推測で状態を決めない
- マージ済みの PR も、メモリーに書かれた方針や TODO がそのまま入ったとは限らない。差分を見て、メモリーの内容が反映されたかを確かめる
- 確認は読み取りだけにする。`git fetch` 以外でリポジトリの状態を変えない

## 3. 振り分ける

| 判定 | 使う場面 | 反映すること |
| --- | --- | --- |
| 残す | 今も有効で、メモリーに置くのが適切 | なし |
| 直す | 有効だが一部が古い、索引の一行説明が本文とずれている、`[[リンク]]` が切れている | 本文・frontmatter・索引を修正 |
| 統合 | 同じ事実を複数のメモリーが持っている（置き場をまたぐ場合も含む） | 残す側に内容を寄せ、もう一方を削除 |
| 昇格 | 毎回守るべきルールや手順になっている | CLAUDE.md か me- スキルに書き、メモリーを削除 |
| 退避 | 作業は終わったが、経緯や調査結果を後で参照したい | `archiveDirectory` に文書として移し、メモリーを削除 |
| 削除 | 終わった作業の進捗、CLAUDE.md・リポジトリ・git 履歴に既にある、事実として誤っている | メモリーを削除 |

メモリーは索引の1行を見て関係ありそうなときにしか本文が読まれない。迷ったら次を当てはめる。

- **昇格か残すか**：やってしまってから本文を読んでも遅いもの（「`yarn lint` を実行しない」など）は昇格。症状が出てから調べれば足りる知識（「CI の Target crashed は一過性」など）は残す
- **昇格先**：`me-keep-ai-doc-up-to-date` の判断フローに従う。プロジェクトの CLAUDE.md が置き場を指定していれば（例：「再発防止のルールは CLAUDE.local.md に追記する」）そちらを優先する
- **重複**：同じ内容が `instructionFiles` か me- スキルにあれば削除。メモリーにしかない Why や経緯は、書き込み先に足してから削除する
- **終わった作業**：PR がマージ・クローズ済みで、内容が反映されており、進捗や TODO しかないなら削除。原因調査の結論や判断の根拠なら退避
- **frontmatter の形式**：旧形式でも読み込みに影響しないので、形式の違いだけでは「直す」にしない
- **user 種別**：基本的に残す。CLAUDE.md と重複している場合だけ削除を提案する

## 4. 承認をもらう

何も変更せずに、置き場ごとの表で一覧を出す。

```markdown
### <projectPath>（<件数>件）

| メモリー | 判定 | 理由 | 反映先 |
| --- | --- | --- | --- |
| project_pj2c6_t33844 | 削除 | PR #2027〜#2038 はすべてマージ済み。進捗の記録のみ | - |
| project_tcj_frontend_yarn_lint_autofix | 昇格 | 実行前に知る必要がある禁止事項 | ~/work/CLAUDE.local.md の tunecorejapan_frontend 節 |

索引の不整合：<missingFiles / orphanFiles / duplicateFiles / 切れたリンク。なければ「なし」>
未確認：<PR の repo が特定できなかったものなど。なければ「なし」>
```

- 「残す」は表の末尾に1行でまとめてよい。理由には根拠になった確認結果（PR の状態、存在しないパスなど）を書く
- 昇格と統合は、書き込み先を読んだうえで追記の文案も見せる
- 承認された行だけを反映する。最初の依頼が「確認なしで反映して」なら、一覧を出してそのまま反映する
- 依頼が特定の変更を指している場合（「索引のずれを直して」など）は、その範囲だけを反映し、ほかの判定は報告にとどめる

## 5. 反映する

途中で止まっても情報が失われないよう、書き込み先を整えてから削除する。

1. 直す・統合・昇格：書き込み先を更新する
2. 退避：`archiveDirectory/YYYYmmdd_<内容>.md` に書く
3. 削除：メモリーのファイルを消す
4. 索引：MEMORY.md の行を消したファイル・直した内容・orphan・missing に合わせる
5. リンク：消したメモリーへの `[[name]]` を直す。昇格・退避したなら移した先を文章で示す

## 6. 確認して報告する

スキャンをもう一度実行し、索引の不整合と切れたリンクが残っていないことを確かめる。

報告すること：

- 判定ごとの件数と、索引の行数の変化
- メモリー以外に書き換えたファイル（git 管理下のものは commit していないこと）
- `~/dotfiles/unix/` 配下を編集した場合は、home-manager の再適用が要ること
- 未確認のまま残したもの

# Memory Inventory

自動メモリーは、MEMORY.md の索引だけが毎回読み込まれ、本文は索引の1行を見て関係ありそうだと判断されたときに読まれる。
そのため、メモリーが増えるほど索引が読み飛ばされやすくなり、古い記述や重複も判断を誤らせる。
このスキルは、メモリーごとに「今もメモリーに置くのが最適か」を判定して整理する。

## 1. スキャンする

```bash
~/.claude/skills/me-memory-inventory/scripts/scan.ts > "$(mktemp -d)/scan.json"
```

出力は JSON で、ファイルを書き換えない。主な項目は次のとおり。

- `stores[]`：プロジェクトごとのメモリー置き場
  - `projectPath`：メモリーが属するディレクトリ（復元できなければ null。そのときは中身から推測し、判断がつかなければユーザーに聞く）
  - `archiveDirectory`：退避先の `~/.agents/<2階層>`
  - `instructionFiles[]`：そのプロジェクトで読み込まれる CLAUDE.md 類
  - `index`：`missingFiles`（索引にあるがファイルがない）、`orphanFiles`（索引にない）、`duplicateFiles`、`lineCount`
  - `memories[]`：`links[].resolved`（`[[name]]` が解決できるか）、`pathReferences[].exists`、`pullRequestReferences`
- `globalInstructions` / `skills[]`：全体の CLAUDE.md と me- スキル

ファイルを編集するときは、各項目の `path` ではなく `editablePath` を使う。
`~/.claude/` 配下は home-manager が Nix store へ張った読み取り専用の symlink で、実体は `~/dotfiles/unix/` 側にあるため。
`editablePath` が null なら編集先が特定できていないので、その項目は提案だけにとどめる。

`HOME` と `CLAUDE_CONFIG_DIR` を変えると、別の場所をスキャンできる。

## 2. 読んで裏を取る

すべてのメモリー本文と、`instructionFiles` と `globalInstructions` を読む。me- スキルは `skills[].description` で守備範囲をつかみ、重複を疑うときだけ本文を読む。

メモリーは書かれた時点の事実なので、外部の状態と突き合わせてから判定する。

- **PR**：`pullRequestReferences` を `gh pr view <URL か番号> --repo <owner/repo> --json state,mergedAt,title` で引く。`#123` だけの参照は、本文やプロジェクトのリポジトリ（`git -C <dir> remote get-url origin`）から repo を特定する。特定できなければ「未確認」として扱い、推測で状態を決めない
  - マージ済みでも、メモリーに書かれた方針や TODO がそのまま入ったとは限らない。`gh pr diff` やタイトルで、メモリーの内容が実際に反映されたかを確かめる。食い違っていれば、反映されなかった部分を「直す」か「残す」の材料にする
- **ブランチ**：本文に出てくるブランチは `git -C <repo> ls-remote --heads origin <branch>` とローカルの `git branch --list` で確かめる
- **パス**：`pathReferences[].exists` が false のものは、消えた worktree や移動したファイルの可能性が高い
- **コマンド・スクリプト・設定キー**：本文で前提にしているものは `command -v`、`grep`、`jq` などで今もあるかを確かめる

確認は読み取りだけにとどめる。`git fetch` 以外でリポジトリの状態を変えるコマンドは使わない。

## 3. 振り分ける

各メモリーに次のどれか1つを付ける。

| 判定 | 使う場面 | 反映すること |
| --- | --- | --- |
| 残す | 今も有効で、メモリーに置くのが適切 | なし |
| 直す | 有効だが一部が古い、索引の一行説明が本文とずれている、`[[リンク]]` が切れている | 本文・frontmatter・索引を修正 |
| 統合 | 同じ事実を複数のメモリーが持っている（置き場をまたぐ場合も含む） | 残す側に内容を寄せ、もう一方を削除 |
| 昇格 | 毎回守るべきルールや手順になっている | CLAUDE.md か me- スキルに書き、メモリーを削除 |
| 退避 | 作業は終わったが、経緯や調査結果を後で参照したい | `archiveDirectory` に文書として移し、メモリーを削除 |
| 削除 | 終わった作業の進捗、CLAUDE.md・リポジトリ・git 履歴に既にある、事実として誤っている | メモリーを削除 |

判断の軸は「将来の会話で、このメモリーの索引の1行を読んだときに役立つか」。迷ったときは次を当てはめる。

- **昇格か残すか**：ミスが起きる前に気づける場面で毎回適用すべきなら昇格。「`yarn lint` を実行しない」「lint-staged をマージ中に単独で実行しない」のように、やってしまってから本文を読んでも遅いものはメモリーに置いても効かないため。症状が出てから調べれば足りる知識（「CI の Target crashed は一過性」など）は、索引から引けるのでメモリーのままでよい
- **昇格先**：`me-keep-ai-doc-up-to-date` の判断フローに従う。ただし、プロジェクトの CLAUDE.md が置き場を指定している場合（例：「再発防止のルールは CLAUDE.local.md に追記する」）はそちらを優先する
- **重複**：同じ内容が `instructionFiles` か me- スキルに既にあれば削除。メモリーの方が詳しい（Why や経緯がある）なら、その差分を CLAUDE.md 側に足してから削除する
- **終わった作業**：PR がすべてマージ・クローズ済みで、メモリーの内容がマージされた中身に反映されており、進捗や TODO の記録しかないなら削除。原因調査の結論や判断の根拠のように後で読み返す価値があるなら退避
- **frontmatter の形式**：旧形式（`type:` がトップレベルなど）でも読み込みには影響しないので、形式の違いだけでは「直す」にしない。ほかの理由で書き換えるときに、あわせて今の形式にそろえる
- **user 種別**：ユーザーの役割や好みは基本的に残す。CLAUDE.md の内容と重複している場合だけ削除を提案する

## 4. 承認をもらう

何も変更せずに、次の形で一覧を出す。置き場ごとに表を分ける。

```markdown
### <projectPath>（<件数>件）

| メモリー | 判定 | 理由 | 反映先 |
| --- | --- | --- | --- |
| project_pj2c6_t33844 | 削除 | PR #2027〜#2038 はすべてマージ済み。進捗の記録のみ | - |
| project_tcj_frontend_yarn_lint_autofix | 昇格 | 実行前に知る必要がある禁止事項 | ~/work/CLAUDE.local.md の tunecorejapan_frontend 節 |

索引の不整合：<missingFiles / orphanFiles / duplicateFiles / 切れたリンク。なければ「なし」>
未確認：<PR の repo が特定できなかったものなど。なければ「なし」>
```

「残す」は件数が多いので、表の末尾に1行でまとめてよい。理由は1行に収め、根拠になった確認結果（PR の状態、存在しないパスなど）を書く。
昇格と統合は、追記する文案もあわせて見せる。書き込み先のファイルを読み、既存の項目に足すのか新しく節を作るのかを決めてから案を作る。

ユーザーの返答で一部だけ承認されたら、承認された行だけを反映する。
最初の依頼で「全部任せる」「確認なしで反映して」と言われていれば、一覧を出したうえでそのまま反映に進んでよい。
依頼が特定の変更を指している場合（「索引のずれを直して」「dotfiles 側の重複を消して」など）は、その範囲だけを承認済みとして反映し、ほかの判定は一覧で報告するにとどめる。

## 5. 反映する

次の順に反映する。先に書き込み先を整えてから削除するので、途中で止まっても情報が失われない。

1. **直す・統合**：残す側を更新する。書き換えるファイルの frontmatter は、メモリーを扱うときのシステム指示の形式にそろえる
2. **昇格**：書き込み先を編集直前に読み直し、ユーザーの変更を取り込んだうえで追記する
3. **退避**：`archiveDirectory/YYYYmmdd_<内容>.md` に書く（日付は退避した日）。ディレクトリがなければ作る
4. **削除**：メモリーのファイルを消す
5. **索引**：MEMORY.md から消したファイルの行を削除し、直した行を更新する。orphan のうち残すものは1行を追加し、missing の行は消す
6. **リンク**：消したメモリーを `[[name]]` で参照している本文を直す。参照先が昇格・退避したなら、移した先を文章で示す

## 6. 確認して報告する

スキャンをもう一度実行し、`missingFiles`・`orphanFiles`・`duplicateFiles`・`links[].resolved == false` が残っていないことを確かめる。

最後に次を報告する。

- 判定ごとの件数と、索引の行数の変化
- 書き換えたメモリー以外のファイル。git 管理下のファイルは commit していないこと（dotfiles など）
- `~/dotfiles/unix/` 配下を編集した場合は、home-manager の再適用が要ること
- 未確認のまま残したもの

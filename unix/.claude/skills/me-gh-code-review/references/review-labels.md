# レビューコメントのラベル

レビューする側（me-gh-code-review）と対応する側（me-gh-address-pr-comments）で、同じ定義を使う。
ラベルは「書いた人がどこまでの対応を期待しているか」を伝えるためのもので、指摘の正しさを保証するものではない。

## 書式

コメントの先頭にラベルを角括弧で書き、半角スペースを空けて本文を続ける。

```
[should] 0 件のときに `items[0]` を参照していて例外になる
[must][security] ユーザー入力をそのまま SQL に埋め込んでいる
```

`security` は重大度ではなく付加タグなので、単独では使わず `must` / `should` / `better` の後ろに付ける。

## ラベル

| ラベル | 基準 | 作者に期待する対応 |
|---|---|---|
| `ask` | 意図や仕様が読み取れず、判断できない | 回答する。回答次第で別ラベルの指摘に変わる |
| `must` | バグ、仕様との食い違いなど、ユーザーへの影響が大きい | マージ前に必ず直す |
| `should` | 放置すると不具合やユーザーの不利益につながる可能性が高い | 原則直す。直さないなら理由を返す |
| `better` | 直すと良くなるが、今のままでも問題はない。明文化された規約・ルールへの違反もここ | 余裕があれば直す。別 PR に回してもよい |
| `imo` | 規約やルールにはなっていないが、保守性に影響する内部的な指摘 | 作者の判断で採否を決める |
| `nits` | タイポ、コメントの誤りなど、動作に影響しない細かい指摘 | 直すのが楽なら直す |
| `security` | セキュリティ上の危険がある（付加タグ） | 組み合わせたラベルに従う。対応の有無にかかわらず返信する |

## 迷ったとき

- `must` と `should` は、影響が確実か可能性かで分ける。再現条件を説明できるなら `must`。
- `should` と `better` は、放置したときに困る人がいるかで分ける。UI/UX の指摘もこの基準でどちらかに振る。
- 規約に書かれているなら `better`、書かれていない好みや設計の意見なら `imo`。
- 仕様との食い違いに見えても、PR 本文やリンク先の issue から仕様を確かめられないなら `must` にせず `ask` にする。仕様を知らないまま断定すると、正しい実装を壊す修正を招く。
